Project Overview

Unsik 프론트엔드 구현 설명서

지금까지 반영한 화면, 라우팅, 백엔드 API 연동, 목데이터 제거, 그리고 유지보수를 고려한 코드 정리 방향을 한눈에 볼 수 있게 정리한 문서입니다. 백엔드 개발자와 프론트 작업자가 현재 상태를 빠르게 공유하는 것을 목표로 합니다.

React 19 TypeScript strict Vite Kakao OAuth Railway Swagger API PWA basics 일부 백엔드 계약 필요

요약

현재 프론트는 로그인, 그룹 방 목록, 그룹별 투표 플로우, 최종 메뉴, 주변 식당 검색까지 연결되어 있습니다.

4개 주요 라우트: 메인, 카카오 콜백, 방 목록, 그룹 투표
16개 현재 프론트에서 호출하는 백엔드 API 범위
0개 방 목록, 추천 후보, 식당 목록에 사용하는 로컬 목데이터
핵심 방향: 백엔드에 있는 데이터는 API로 가져오고, 백엔드 계약이 없는 데이터는 억지로 프론트에서 저장하거나 가짜로 채우지 않습니다. 그래서 없는 기능은 명확한 빈 상태나 API 필요 상태로 보여줍니다.

작업 내역

최근 작업은 기능별로 분리되어 있어 어떤 변경이 어떤 목적을 가지는지 추적하기 쉽습니다.

메인 화면 정리 메뉴 점 보러 가기 버튼을 제거하고, 첫 화면의 핵심 액션을 카카오로 시작하기로 정리했습니다.
공통 백엔드 클라이언트 추가 src/services/backend.ts에 API 호출, 타입, 파서, 에러 처리를 모아 화면 코드와 통신 코드를 분리했습니다.
방 목록 API 연동 기존 로컬 방 목데이터를 제거하고 그룹 조회, 생성, 초대코드 참여, 삭제, 멤버 조회를 백엔드 API 기준으로 바꿨습니다.
그룹 투표 플로우 추가 투표 생성, 참여자 선택, 오늘의 취향 입력, 추천 후보, 호불호 투표, 최종 메뉴, 식당 검색 화면을 추가했습니다.
라우팅 연결 /groups/:groupId/votes 경로를 추가해서 방 목록에서 해당 그룹 투표 화면으로 이동할 수 있게 했습니다.
초대 링크와 PWA 기본 구성 /grouplist?code=... 초대 링크 자동 참여, 웹 앱 매니페스트, 서비스 워커, 설치 아이콘을 추가했습니다.
문서화 API 연동 현황과 Swagger에 아직 없는 계약을 docs/ai/project-context.md에 정리했습니다.

구조

큰 프레임은 단순하게 유지하고, 변경 가능성이 큰 API 통신과 화면 상태는 분리했습니다.

라우팅

React Router를 추가하지 않고 src/App.tsx에서 작은 라우트 유니온 타입으로 관리합니다. 현재 경로는 /main, /auth/kakao/callback, /grouplist, /groups/:groupId/votes입니다.

API 경계

모든 백엔드 호출은 src/services/backend.ts로 모았습니다. 화면 컴포넌트는 listGroups, createVote, recommendMenus 같은 의도 중심 함수만 호출합니다.

화면 분리

방 목록은 src/components/rooms, 투표 흐름은 src/components/votes에 둬서 화면별 책임을 분리했습니다.

목데이터 정책

실제 DB 기반으로 조회할 수 있는 영역은 API만 사용합니다. API가 없는 이전 식사 기록, 평점, 리뷰, 점수 설명은 프론트에서 가짜로 만들지 않습니다.

초대 링크

/grouplist?code=...를 읽어 로그인 전이면 localStorage에 잠시 보관하고, 로그인 후 POST /api/groups/join으로 자동 참여합니다.

PWA 경계

src/pwa.ts는 프로덕션에서만 서비스 워커를 등록합니다. 서비스 워커는 앱 셸과 정적 파일만 캐시하고, /api/* 요청은 네트워크 원본을 사용합니다.

사용 흐름

사용자가 실제로 타는 화면 흐름과 API 호출 순서를 분리해서 보면 디버깅이 쉽습니다.

메인 화면
  -> 카카오 로그인
  -> /auth/kakao/callback
  -> /grouplist
  -> 그룹 생성 또는 초대코드 참여
  -> /groups/:groupId/votes
  -> 투표 생성
  -> 참여자 선택
  -> 오늘의 취향 제출
  -> 메뉴 추천 실행
  -> 후보 카드 호불호 투표
  -> 최종 메뉴 확정
  -> 주변 식당 검색

오늘의 취향

GET /api/menus로 전체 메뉴 목록을 가져와 검색 UI에 보여줍니다. 사용자가 특정 메뉴를 제외하면 현재 API 제약상 그 메뉴의 cuisine을 dislikedCuisines로 변환해 제출합니다.

메뉴 추첨

프론트가 /api/menus에서 직접 랜덤으로 고르지 않습니다. POST /api/votes/{voteId}/recommend 호출 후 백엔드가 DB 메뉴 테이블과 선호 조건을 기준으로 후보 3개를 내려줍니다.

좋아/싫어 투표

추천 후보가 나온 뒤 누르는 좋아/싫어는 최종 메뉴 집계용입니다. POST /api/votes/{voteId}/ballots로 후보 메뉴 ID별 LIKE 또는 DISLIKE를 제출합니다.

추천 식당

최종 메뉴가 정해진 뒤 GET /api/restaurants?menu=...&voteId=...&page=1를 호출합니다. 응답은 카카오 로컬 장소 문서라서 평점, 가격대, 리뷰 수는 현재 표시하지 않습니다.

API 연동

아래 표는 현재 프론트에서 실제로 쓰는 API와 화면에서의 역할입니다.

API 프론트 함수 사용 위치 역할
POST /api/auth/kakao authenticateWithKakaoCode 카카오 콜백 카카오 OAuth code와 같은 로그인 요청에 사용한 redirectUri를 백엔드 세션 토큰과 회원 정보로 교환합니다.
로컬 로그아웃 clearAuthSession 방 목록 현재 기기의 unsik:auth_session만 삭제하고 메인 화면으로 돌아갑니다.
GET /api/groups listGroups 방 목록 로그인한 사용자가 속한 그룹 목록을 조회합니다.
POST /api/groups createGroup 방 만들기 새 그룹을 만들고 방 목록에 추가합니다.
POST /api/groups/join joinGroup 코드로 참여하기 초대코드로 기존 그룹에 참여합니다.
DELETE /api/groups/{groupId} deleteGroup 방 삭제 방장 권한 기준으로 그룹과 관련 데이터를 삭제합니다.
GET /api/groups/{groupId}/members listGroupMembers 방 목록 인원, 투표 참여자 선택 그룹 멤버 수와 투표 참여자 후보를 조회합니다.
GET /api/menus listMenus 오늘의 취향 검색 가능한 메뉴 카탈로그를 가져옵니다. 추천 후보를 직접 뽑는 API는 아닙니다.
POST /api/groups/{groupId}/votes createVote 투표 생성 투표 제목, 마감 시간, 학교 코드, 참여자 ID를 보내 투표를 만듭니다.
GET /api/groups/{groupId}/votes listGroupVotes 투표 목록 현재 그룹에 속한 투표 요약 목록을 불러옵니다.
POST /api/votes/{voteId}/preferences submitPreference 오늘의 취향 제출 싫어하는 cuisine과 알레르기/제한 정보를 제출합니다.
POST /api/votes/{voteId}/recommend recommendMenus 추천 실행 백엔드가 조건에 맞는 후보 메뉴를 내려줍니다.
POST /api/votes/{voteId}/ballots submitBallot 후보 카드 투표 후보 메뉴별 좋아/싫어 값을 제출합니다.
GET /api/votes/{voteId} getVote 최종 메뉴 확인 집계 후 결과 메뉴가 이미 생겼는지 확인합니다.
GET /api/votes/{voteId}/pending-members listPendingPreferenceMembers 투표 현황 선호 미제출자를 조회해서 현황 카드의 프로필 체크 표시를 채웁니다.
DELETE /api/votes/{voteId} deleteVote 투표 삭제 그룹장이 투표 목록의 더보기 메뉴에서 상태와 관계없이 투표를 삭제하고 화면 목록에서 제거합니다.
GET /api/restaurants searchRestaurants 최종 메뉴 화면 확정 메뉴와 투표 위치 기준으로 주변 식당을 거리순 조회합니다.
참고: POST /api/menus는 현재 프론트 사용자 화면에서 쓰지 않습니다. 백엔드 메뉴 DB에 메뉴를 추가하는 시드 또는 관리자 성격의 API로 보는 게 맞습니다.

유지보수 기준

이번 작업은 단순히 화면을 붙이는 것보다, 나중에 백엔드 계약이 늘어났을 때 바꾸기 쉬운 구조를 우선했습니다.

타입 먼저 고정

Cuisine, Restriction, School, VoteStatus 같은 Swagger enum을 TypeScript 타입으로 고정해 잘못된 문자열이 화면 전체로 퍼지는 것을 줄였습니다.

파서로 응답 방어

백엔드 응답은 unknown으로 받은 뒤 parseGroupResponse, parseVoteDetailResponse 같은 함수에서 화면이 기대하는 형태로 정규화합니다.

화면은 의도만 호출

컴포넌트 안에서 fetch URL을 직접 조립하지 않고 backend.ts의 함수만 호출합니다. API 경로가 바뀌면 대부분 서비스 파일만 수정하면 됩니다.

없는 데이터는 없는 대로 표시

평점, 리뷰, 이전 식사 기록처럼 API가 없는 정보는 가짜 데이터를 만들지 않고 명확한 빈 상태나 백엔드 필요 안내로 처리했습니다.

중복 호출 완화

호불호 투표는 후보 카드 클릭 때 바로 제출하지 않고, 최종 확정 단계에서 제출합니다. 다시 뽑기나 중복 마감으로 생기던 충돌 가능성을 줄였습니다.

검증 명령 유지

변경 후 npm.cmd run typecheck, npm.cmd run lint, npm.cmd run build를 통과한 상태를 기준으로 커밋했습니다.

면접 대비

이 프로젝트를 설명할 때는 단순히 “API를 붙였다”보다, 어떤 기술 선택을 했고 왜 유지보수에 유리한지까지 말하는 것이 좋습니다.

React 컴포넌트 구조

화면 단위 책임을 main, auth, rooms, votes로 나눴습니다. 그래서 방 목록 수정이 투표 화면에 영향을 덜 주고, 새 화면이 생겨도 기존 구조 안에 기능별로 추가할 수 있습니다.

TypeScript strict

Swagger enum을 Cuisine, Restriction, School, VoteStatus 같은 유니온 타입으로 고정했습니다. API 값이 화면 전반에 문자열로 흩어지지 않게 만들어 변경 비용을 줄였습니다.

API 서비스 계층

컴포넌트에서 직접 fetch를 호출하지 않고 src/services/backend.ts에 모았습니다. API 경로, 요청 body, 응답 파싱, 에러 처리를 한 곳에서 관리할 수 있어 Swagger 변경 대응이 쉽습니다.

방어적 응답 파싱

백엔드 응답을 바로 믿고 쓰지 않고 unknown으로 받은 뒤 파서에서 정규화합니다. 응답 필드가 비거나 일부 누락돼도 화면이 바로 깨지지 않도록 기본값과 enum 검증을 둔 구조입니다.

라우팅 선택

현재 라우트 수가 적어서 React Router를 추가하지 않고 AppRoute 유니온 타입과 History API로 처리했습니다. 의존성을 늘리기보다 현재 규모에 맞는 단순한 구조를 선택했습니다.

목데이터 제거 기준

DB에 있는 정보는 API 응답만 신뢰하고, 없는 정보는 프론트에서 억지로 저장하지 않았습니다. 투표 목록도 GET /api/groups/{groupId}/votes 응답으로 채우고 localStorage에 따로 복제하지 않습니다.

사용자 상태 처리

데이터가 필요한 화면에는 로딩, 빈 상태, 에러 메시지를 둬서 API 실패 시에도 사용자가 현재 상태를 이해할 수 있게 했습니다. 특히 식당 검색 결과가 비면 가짜 식당을 넣지 않고 빈 결과 안내를 보여줍니다.

검증 가능한 개발 흐름

변경 후 typecheck, lint, build를 통과한 상태로 커밋했습니다. 타입 안정성, 코드 규칙, 실제 번들 빌드를 각각 확인하는 흐름입니다.

예상 질문 답변 포인트 코드 근거
왜 API 호출을 컴포넌트 안에 직접 넣지 않았나요? 화면은 사용자 흐름과 상태에 집중하고, 통신 세부사항은 서비스 계층에 모으기 위해서입니다. API가 바뀌면 컴포넌트 전체를 뒤지지 않고 backend.ts 중심으로 수정할 수 있습니다. src/services/backend.ts, listGroups, createVote, recommendMenus
왜 투표 목록을 localStorage에 저장하지 않았나요? 투표는 DB 기준 데이터라서 프론트 임시 저장으로 맞춘 것처럼 보이면 실제 데이터와 어긋날 수 있습니다. 현재는 GET /api/groups/{groupId}/votes 응답으로 현재 그룹의 투표 요약을 조회합니다. listGroupVotes, VoteSummaryResponse
TypeScript를 어떻게 유지보수에 활용했나요? 백엔드 enum과 응답 형태를 타입으로 고정해 잘못된 값이 컴파일 단계에서 드러나게 했습니다. 화면에서는 Cuisine, School 같은 명확한 도메인 타입을 사용합니다. Cuisine, Restriction, School, VoteStatus
추천 메뉴와 전체 메뉴 조회의 차이는 무엇인가요? GET /api/menus는 오늘의 취향 화면에서 검색용 메뉴 카탈로그를 보여주는 API입니다. 실제 후보 추첨은 POST /api/votes/{voteId}/recommend가 백엔드 DB와 선호 조건을 보고 처리합니다. listMenus, submitPreference, recommendMenus
백엔드에 없는 데이터는 어떻게 처리했나요? 평점, 리뷰, 이전 식사 기록, 점수 설명처럼 API에 없는 데이터는 프론트에서 꾸며내지 않았습니다. 대신 빈 상태나 “API 필요” 메시지로 처리해 실제 데이터 신뢰도를 지켰습니다. 식당 상세, 점수 상세, 이전 기록
호불호 투표 충돌은 어떻게 줄였나요? 후보 카드 클릭 시마다 바로 ballot을 보내지 않고, 최종 확정 버튼에서 한 번 제출하도록 했습니다. 이후 GET /api/votes/{voteId}로 결과가 이미 생겼는지 확인하고, 백엔드가 resultMenu를 내려줄 때만 최종 화면으로 이동합니다. submitBallot, getVote
왜 React Router를 쓰지 않았나요? 현재 경로가 적고 요구사항이 단순해서 별도 라우팅 라이브러리보다 작은 라우트 유니온 타입이 더 가볍다고 봤습니다. 라우트가 늘어나거나 중첩 라우팅이 필요해지면 React Router 도입을 검토할 수 있습니다. AppRoute, getAppRoute, getRoutePath
면접 답변 한 줄 요약: 이 프로젝트에서는 화면과 API 경계를 분리하고, 백엔드 계약을 TypeScript 타입과 파서로 감싸서 변경에 강하게 만들었으며, API가 없는 데이터는 목데이터로 숨기지 않고 계약 공백으로 드러내는 방향으로 유지보수성을 챙겼습니다.

남은 백엔드 계약

프론트에서 임시 저장이나 목데이터로 해결하지 않고, 백엔드 API가 생겨야 제대로 완성되는 부분입니다.

필요 API 또는 필드 필요한 이유 현재 프론트 처리
투표 단계별 제출 상태 누가 선호를 냈는지, 누가 호불호 투표를 했는지 정확히 보여줘야 합니다. 현재는 선택된 참여자 수와 진행 중 상태만 보여주고, 단계별 미제출자는 표시하지 않습니다.
dislikedMenuIds 김치찌개만 제외하고 한식 전체는 허용하는 식의 메뉴 단위 제외가 필요합니다. 현재는 선택 메뉴의 cuisine을 dislikedCuisines로 바꿔 제출합니다.
식당 검색 fallback 간장치킨 같은 구체적 메뉴명으로 검색 결과가 없으면 치킨, 패스트푸드, 음식점 순으로 재검색할 필요가 있습니다. documents가 빈 배열이면 추천 식당 없음 상태를 보여줍니다.
식당 상세 정보 평점, 리뷰 수, 가격대, 영업 상태를 보여주려면 카카오 로컬 응답 이상의 데이터가 필요합니다. 현재 응답에 있는 주소, 전화, 거리, 카카오맵 링크만 표시합니다.
그룹 수정 API 방 이름, 아이콘, 최대 인원 같은 설정을 수정하려면 별도 API가 필요합니다. 이름 변경 메뉴는 제거했고, 아이콘/최대 인원은 생성 시 description 텍스트에만 담깁니다.
푸시 알림 구독/전송 API 투표 알림을 실제 사용자 기기로 보내려면 서비스 워커 push subscription과 백엔드 발송이 필요합니다. 현재는 브라우저 Notification API로 즉시 로컬 알림만 시도합니다.
현재 쓰지 않는 Vote API 이유 현재 대체 흐름
GET /api/votes/my 투표 목록을 로그인 회원 전체 기준이 아니라 현재 그룹 기준으로 보여줘야 합니다. GET /api/groups/{groupId}/votes로 그룹 투표 목록을 조회합니다.
POST /api/votes/{voteId}/close 방장 강제 마감 API라 일반 호불호 투표 흐름에서는 사용하지 않습니다. 전원이 투표하면 백엔드가 자동 집계하고, 프론트는 GET /api/votes/{voteId}의 resultMenu를 기다립니다.

주요 파일

수정할 때 먼저 볼 파일입니다.

src/App.tsx

최상위 라우팅과 로그인 세션 전달을 담당합니다.

src/services/auth.ts

카카오 로그인 URL, OAuth callback 교환, 브라우저 세션 저장을 담당합니다.

src/services/backend.ts

Swagger API 호출, 응답 파싱, 공통 에러 처리를 담당합니다.

src/pwa.ts

프로덕션 빌드에서만 서비스 워커를 등록해 개발 중 캐시 문제를 피합니다.

src/components/rooms

그룹 방 목록, 방 생성, 코드 참여, 삭제 UI를 담당합니다.

src/components/votes

투표 목록, 투표 생성, 선호 입력, 후보 투표, 결과, 식당 상세 화면을 담당합니다.

public/manifest.webmanifest

설치 가능한 웹 앱 이름, 시작 URL, 표시 모드, 아이콘 정보를 정의합니다.

public/service-worker.js

앱 셸과 정적 자산을 캐시하고, API 요청은 캐시하지 않습니다.

docs/ai/project-context.md

AI 작업자가 읽는 최신 프로젝트 맥락과 API 계약 공백을 정리합니다.

이 문서는 docs/project-implementation-overview.html입니다. 브라우저에서 바로 열어 확인할 수 있습니다.
